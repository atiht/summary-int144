WEEK 1 Agile Principles & Scrum Concepts

⚡ Agile Manifesto (4 Values)

  • •
    Individuals & interactions over processes & tools (สำคัญเท่ากันทั้งคู่!)
  • •
    Working software over comprehensive documentation
  • •
    Customer collaboration over contract negotiation
  • •
    Responding to change over following a plan
  • •
    จำขึ้นใจ: ฝั่งขวา (Plan, Doc, Contract, Process) ยังสำคัญและยังต้องทำ แค่ให้คุณค่าฝั่งซ้ายมากกว่า

📐 Timeboxing & DSDM Triangle

  • •
    Timeboxing = จัดการเวลาด้วย Hard Deadline งานไม่เสร็จ ห้ามขยายเวลาเด็ดขาด
  • •
    Traditional = ล็อก Features ตายตัว → เวลาและงบบานปลาย
  • •
    DSDM Approach = ล็อก Time, Cost, Quality คงที่ → ปรับยืดหยุ่นตัวแปร Features (Vary)
  • •
    Stepwise Refinement = โฟกัสเรื่องสำคัญสุดก่อน ทำทีละ Feature by Feature

💎 คีย์เวิร์ด 12 Agile Principles & Heart of Agile

  • •
    ข้อ 1 Satisfy Customer: ส่งมอบซอฟต์แวร์ที่มี Value อย่างต่อเนื่องสม่ำเสมอ (ไม่ใช่ลดงบ/ลดราคา)
  • •
    ข้อ 2 Deliver Frequently: ใช้คำว่า Deliver (ไม่ใช่ Release เพราะ Release เป็นสิทธิ์ฝั่งลูกค้า)
  • •
    ข้อ 6 & 9 & 10: สื่อสารดีสุดคือ Face-to-face | Simplicity = ลดงานที่ไม่จำเป็น | Working software คือตัววัดความก้าวหน้าหลัก (ข้อ 10)
  • •
    Heart of Agile (4 คำ) = Collaborate, Deliver, Reflect, Improve (ไม่มีคำว่า Estimate!)

🏛️ ต้นกำเนิด Scrum & 3 เสาหลัก Empirical

  • •
    New Product Dev Game: หัวใจคือ Speed and Flexibility ทำงานแบบทีมรักบี้ (เคลื่อนที่เป็นก้อนเดียวกัน)
  • •
    Scrum คือ: Lightweight, Simple to understand, Difficult to master
  • •
    3 Empirical Pillars (ออกสอบชัวร์):
    1. Transparency เห็นชัดเจน + เข้าใจตรงกันด้วยมาตรฐานเดียวกัน (เช่น DoD)
    2. Inspection ตรวจหาความเบี่ยงเบนบ่อยๆ
    3. Adaptation ปรับแก้ให้เร็วที่สุดเมื่อออกนอกลู่ทาง

WEEK 2 Scrum Overview, Phases & Events

🔄 3 Scrum Phases & การวางแผน

  • •
    Pregame (Planning & Architecture) = Defined process
  • •
    Game (Development Sprints) = Empirical process เพียงเฟสเดียว!
  • •
    Postgame (Closure / เตรียมปล่อยระบบ) = Defined process
  • •
    การวางแผนใน Scrum: ไม่ใช้ Detailed Up-front ล้วน (เพราะเกิด WASTE) และไม่ใช้ JIT ล้วน แต่ต้อง Balance Up-front & Just-in-Time
  • •
    Multilevel Planning: Vision → Roadmap → Release → Sprint → Daily

👥 Accountability vs Responsibility & Team

  • •
    Responsibility = หน้าที่ว่าใครทำชิ้นไหน (Who does what tasks) แชร์กันได้
  • •
    Accountability = ความเป็นเจ้าของผลลัพธ์สุดท้าย (Ownership of the outcome)
  • •
    การส่งมอบ Increment: เป็น Accountability ของ ทั้ง Scrum Team ร่วมกัน (ไม่มีหัวหน้าหรือคนเดียวรับผิดชอบ)
  • •
    Cross-functional = รวมกันทั้งทีม (Collectively) แล้วมีทักษะครบ (ไม่ต้องเก่งทุกอย่างในคนเดียว)
  • •
    Self-managing = ทีมตัดสินใจกันเองว่าใครทำอะไร เมื่อไหร่ อย่างไร
Scrum Event เมื่อไหร่ 4 สัปดาห์ 2 สัปดาห์ 1 สัปดาห์ จุดเน้นสำคัญ (ออกสอบ)
Sprint ต่อเนื่องทันที 4 wks 2 wks 1 wk ระยะเวลาต้องคงที่ (Consistent duration) ไม่เปลี่ยนไปมา
Sprint Planning วันแรกของ Sprint 8 ชม. (4+4) 4 ชม. (2+2) 2 ชม. (1+1) ตอบ What & How / Dev เป็นผู้ทำ Commitment (PO/SM บังคับไม่ได้)

WEEK 3 Product Backlog, User Stories, DEEP & MoSCoW

📝 Product Backlog & User Story

  • •
    Product Backlog: ถังรวมงานที่เดียวของ Product (Single source of work) มี 4 Attributes: Description, Order, Estimate, Value
  • •
    Never Complete: ไม่มีวันเสร็จสมบูรณ์ จนกว่าตัว Product จะ Retire (เลิกใช้งาน)
  • •
    User Story (ต้องมี 3 ส่วน):
    As a <Role>, I want to <Action> so that <Benefit/Value>
  • •
    จุดประสงค์ User Story: เป็นตัวตั้งต้นในการพูดคุย (Placeholder for a conversation) กับ PO
  • •
    ลำดับขนาด: Epics (เดือน) → Features (สัปดาห์) → Stories (วัน) → Tasks (ชม.)

🔍 คุณลักษณะ DEEP & 7 วิธีหั่น PBI

  • •
    Detailed appropriately = ตัวบนที่จะทำเร็วๆ นี้เล็กและละเอียดมาก ส่วนตัวล่างใหญ่และยังไม่ต้องละเอียด (ไม่เท่ากันทุกตัว!)
  • •
    Emergent = อัปเดตตลอดเวลา | Estimated = ประเมินขนาดแล้ว | Prioritized = จัดลำดับตาม Value, Size, Risk, Learn Fast
  • •
    การหั่น PBI (Splitting): หั่นแนวตั้งให้แต่ละชิ้นยังเป็น Working, demonstrable software (ไม่หั่นแยกเป็น Technical task)
  • •
    7 วิธีหั่น: 1) Operations (CRUD) 2) Roles 3) Data types/parameters 4) Workflow steps 5) Happy/Unhappy flow 6) Business rules 7) Optimize now vs later

📊 Fixed Date Release & MoSCoW

  • •
    MRFs (Minimum Releasable Features) = ชุดฟีเจอร์ Must-have เล็กที่สุดที่ต้องมี ควรตั้งไว้ที่ 60%–70% ของเวลาทั้งหมด (เผื่อ Delay และ Emergent MRF)
  • •
    Must have (~60%) = ขาดไม่ได้เด็ดขาด ไม่มี Workaround (No workaround)
  • •
    Should have (~20%) = สำคัญแต่ไม่วิกฤต มี Workaround ชั่วคราว ได้
  • •
    Could have (~20%) = น่ามีแต่ผลกระทบน้อยกว่า เป็น Buffer
  • •
    Won't have (this time) = ตกลงว่ายังไม่ทำในรอบนี้ (แต่อาจทำใน Release ถัดไปได้!)
🔥 จุดหลอก Menti Week 3 ที่ อ.โอฬาร เน้น
❌ หลอก: User Story มีแค่ 2 ส่วน (Role + Action) → ตอบ: ผิด (ต้องมี so that Benefit/Value เป็นส่วนที่ 3)
❌ หลอก: ตัว D ใน DEEP คือ Detailed and documented → ตอบ: ผิด (คือ Detailed appropriately)
❌ หลอก: PBI ทุกตัวใน Backlog ต้องมีรายละเอียดเท่ากัน → ตอบ: ผิด (ตัวบนละเอียดกว่าตัวล่าง)
❌ หลอก: Won't have แปลว่าตัดทิ้งถาวรไม่ทำอีกเลย → ตอบ: ผิด (อาจเป็น Must-have ใน Release 2 ได้)
WEEK 4 Scrum Sprints, Capacity, Spike & Execution

🎯 Sprint Goal, DoD vs Acceptance Criteria

  • •
    ระหว่าง Sprint: Scope ปรับคุยกับ PO ได้ถ้าไม่กระทบ Sprint Goal และคุณภาพห้ามลดลง
  • •
    Sprint Backlog = Sprint Goal + Selected PBIs + Tasks (แต่ละ Task ≤ 8 ชม.) *ไม่รวม DoD*
  • •
    Definition of Done (DoD) = Checklist มาตรฐานกลางที่บังคับใช้กับ ทุกๆ PBI (Applies to ALL PBIs)
  • •
    Acceptance Criteria = เงื่อนไขตรวจรับเฉพาะของแต่ละ PBI (Item-specific) เขียนได้แบบ Scenario (Given/When/Then) หรือ Rule-oriented

🧮 Team Capacity & การทำ Spike

  • •
    การคิด Capacity: ห้ามตั้งเต็ม 80 ชม. ใน 2 สัปดาห์! ต้องหัก: เวลาลาส่วนตัว + งานนอก Sprint + เวลาประชุม Scrum Events + กัน Sprint Buffer เผื่องานงอก (Unplanned work)
  • •
    กฎเหล็ก: "Don't start what you cannot finish"
  • •
    Spike = กิจกรรมหาความรู้ (PoC / Prototype) เมื่อประเมินหรือแตก Task ไม่ได้:
    • Technical Spike: ถามว่าสร้างอย่างไร / ใช้อะไร (How/Which)
    • Functional Spike: ถามว่าระบบและผู้ใช้ควรทำงานอย่างไร (Behavior)

⚙️ Execution, Task Board & Technical Debt

  • •
    ห้ามทำ Mini Waterfall! (วิเคราะห์รวดเดียว → โค้ดรวดเดียว → เทสต์วันสุดท้าย = พังเมื่อหมดเวลา)
  • •
    Swarming = คนที่ว่างมารุมช่วยทำ PBI ที่เปิดค้างไว้ให้จบก่อนเปิดงานใหม่
  • •
    Pair / Triple Programming = ช่วยให้ได้ Fast feedback และกระจายความรู้ (ควรสลับ Role FE/BE ทุก Sprint หรือทุก PBI)
  • •
    Task Board: มีอย่างน้อย 3 สถานะ (To-do, Doing, Done) + ใส่ Assignee + แนบ Artefacts
  • •
    Technical Debt = ทางลัด/โครงสร้างแย่ (เช่น ชื่อตัวแปรแย่, Hard-code URL, CORS allow all, ไม่ดัก Exception, รัน FE ด้วย node.js บน Prod) → แก้ด้วย Code Refactoring

❌ หลอก: Definition of Done (DoD) นับเป็นส่วนหนึ่งของ Sprint Backlog → ตอบ: ผิด (เป็นข้อตกลงกลาง ไม่ใช่งานใน Sprint Backlog)
❌ หลอก: ห้ามเปลี่ยนอะไรเลยใน Sprint แม้ไม่กระทบ Sprint Goal → ตอบ: ผิด (เปลี่ยนได้ถ้าไม่กระทบ Sprint Goal)

❌ หลอก: ทำ Mini Waterfall ใน Sprint ได้ → ตอบ: ผิด (Mini Waterfall is a bad idea)
WEEK 5 Scrum Values, Working Team & Roles

❤️ 5 Scrum Values & Working Team

  • •
    5 Scrum Values = Commitment, Focus, Courage, Openness, Respect → สร้าง TRUST
  • •
    สมการความเชื่อใจ: Trust = (Credibility + Reliability + Intimacy) / Self-Orientation
  • •
    Working Group = ผู้นำเดี่ยวสั่งการ, รับผิดชอบเดี่ยว, ผลงานแยกชิ้น (Individual work products)
  • •
    Working Team = แชร์ภาวะผู้นำ, รับผิดชอบร่วมกัน, ผลงานเป็นของส่วนรวม (Collective work products)

🛠️ 10 ลักษณะของ Developers & ขนาดทีม

  • •
    ขนาดทีม (Right-sized): กฎทั่วไปคือ 5–9 คน (หรือใน Scrum Guide ≤ 10 คน) ลดปัญหาคนกินแรงเพื่อน (Social loafing)
  • •
    T-shaped skills = รู้ลึกในสายหลัก + รู้กว้างพร้อมข้ามไปช่วยสายอื่น
  • •
    Musketeer attitude = "All for one and one for all" ลงเรือลำเดียวกัน
  • •
    Focused & Sustainable pace: ไม่ถือหลายโปรเจกต์พร้อมกันเกินไป และทำงานด้วยจังหวะที่ยั่งยืน

👑 Product Owner (PO) vs Scrum Master (SM)

  • •
    Product Owner (6 หน้าที่หลัก): Maximize product value, Manage economics, Participate in planning, Groom backlog, Define & verify acceptance criteria, Collaborate กับทีมและ Stakeholders (ห้ามสั่ง Assign งานย่อยให้ Dev!)
  • •
    Scrum Master (6 หน้าที่หลัก):
    1. Coach (เน้นถาม ASK เพื่อให้ทีมแก้ปัญหาเอง)
    2. Servant leader
    3. Process authority (ดูแลกระบวนการ สั่งงานไม่ได้ ไม่ใช่คนคอยตามจี้งาน)
    4. Interference shield (กันคนนอกมาดึงคนในทีมกลาง Sprint)
    5. Impediment remover (แก้อุปสรรคที่เกินอำนาจทีม เช่น คุยกับ VP Operations เรื่อง Server พัง)
    6. Change agent (ผู้นำการเปลี่ยนแปลงทั้งในทีมและระดับ Organization)
